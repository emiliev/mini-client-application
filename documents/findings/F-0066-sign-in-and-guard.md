# F-0066: The sign-in form and the `/me/**` guard: what go_router does to a guarded push, why the guard ticks on sign-out only, and how `from` can never be an open redirect

- **Date:** 2026-11-27
- **Author:** crew: Engineer (T-0066)
- **Type:** Design record / Lesson
- **Related:** T-0066, P-044, P-094, P-110, plan 01 §4.2 and F045; F-0048, F-0049 (notes 10 and 11), F-0050, F-0063

## Summary
`auth_signin` (feature, archetype FW with one page) replaces the fixture sign-in sheet. `app_core` owns the guard (`SignInGuard`), the `from` check (`safeSignInTarget`) and the callers' hook (`requestAppSignIn`, over `AppFlows.signIn`); `account_wiring` owns the route (`/auth/sign-in?from=&reason=`). Sections 1 to 5 are what the next guarded group (`/library/**`, `/store/checkout`) needs; sections 6 to 9 are traps found on the way.

## 1. The shape
- **Route:** `SignInRoute(from, reason)` in `account_wiring` builds `FlowResultRoute<bool>` around `AuthSignInFlow`. `true` means signed in. Without `from`, the route completes (pops with the bool): this is what a feature's `requestSignIn()` awaits (`requestAppSignIn` returns true only when the screen said "signed in" **and** a session exists). With `from`, a sign-in does `router.go(safeSignInTarget(from))` instead of completing; "Not now" always completes with false (pops, so a cold link ends at home because `nestUnderHome` put home below it).
- **Guard:** the one `redirect` in `buildAppRouter` asks `SignInGuard.redirect(uri)`: signed out and `/me/**`, `/library/**` or `/store/checkout` gives `/auth/sign-in?from=<path+query+fragment>` (a running link's `miniclient://app` is stripped). Signed in, or an open location, gives null. A signed-out user is never redirected away from the sign-in route. A **signed-in** user sent there (a link, a `go`) is redirected on to `safeSignInTarget(from)` (home when `from` is absent or foreign): there is nothing to sign in to. This runs only when a location is parsed, and a sign-in does not refresh the router, so the page of a sign-in under way is not moved by its own session.
- **Reason:** `?reason=<SignInPurpose name>` is a closed set of codes (`favourites`, `readingLists`, `cart`, `triviaResults`, `appearanceSync`) that the feature maps to its own strings. A link must not be able to put its own words on the screen, so an unknown code says nothing (`SignInReason.parse`). It keeps the old sheet's per-caller line ("to keep your favourites").
- **Package name:** `auth_signin`, not `auth_sign_in` (see 7).

## 2. A redirected push, and what its pop value does
A signed-out `AppFlows.createReadingList(router)` is a push of `/me/lists/new`; the guard shows the sign-in page in its place. go_router chains the push's future to the page the **redirect** shows (F-0049 note 7), so a value the sign-in page pops with reaches the **original caller**. The first version of the route popped `'cancelled'` (a `String`), and `createReadingList` returned it as a list id. Rule: **`AppFlows._open<T>` accepts a pop value only of its own result type**, and the sign-in route's result is a `bool`, which is null to every `String` caller (tested: `sign_in_guard_router_test` "a push guarded, then Not now: null once").

## 3. A refresh does not re-evaluate a pushed page; a sign-in must not refresh at all
- `GoRouter.refresh()` (what `refreshListenable` does) restores the saved match list. Restoring an **imperative** page (a `push`, which is how `AppFlows` opens an editor) does not run `redirect` for it again. So `refreshListenable` alone never moves a signed-out user off a pushed `/me/lists/l-1/edit`. `SignInGuard.bind(router)` adds the missing half: after a **sign-out** it walks **every** page of the stack after the next frame (`ImperativeRouteMatch.matches.uri` for a pushed page) and `go`es to sign-in when any is protected, with `from` set to the **topmost protected** page, so Back never reaches a protected page left under an open one (tested: editor, an open page on top, sign out). The `go` replaces the stack, so each waiting `AppFlows` caller completes once with null.
- The guard ticks `refreshListenable` on a **sign-out only**. A refresh that starts with a sign-in restores the stack as it was when it started; if the sign-in page pops in the next few frames (the flow completed right after the session change), the late restore **brings the page back**. The test `sign_in_guard_router_test` "a sign-in answered in the same turn as the session change" pins it. In the app the session is saved before `AuthApi.signIn` returns, so the window is small, but "small" is the wrong thing for a security screen.
- The guard listens to the session only while the router listens to `refresh` (`addListener`/`removeListener` on a `ChangeNotifier`), so nothing is left after `router.dispose()` (tested).
- After a pop, go_router keeps the **query of the link it popped away from** on the router's uri: Not now on a cold link leaves `router.state.uri` as `/?from=%2Fme%2Flists%2Fnew` (the screen is home). Tests compare the path.

## 4. `from` and the open redirect
`safeSignInTarget(from)` is the only place a `from` becomes a navigation. It accepts a path starting with exactly one `/`, or `miniclient://app/…` with no user-info or port, and returns the path, query and fragment **as written** (an encoded segment is not decoded or re-encoded). It returns home for everything else:
- another scheme or host (`https://evil.com`, `javascript:`, `data:`, `file:`, `miniclient://evil/…`, `miniclient://app@evil.com/…`, `miniclient://app:8080/…`), scheme-relative (`//evil`, `///evil`), relative (`evil.com`, `../x`, `?x`, `#x`);
- a backslash (`/\evil`, `\\evil`), a control character or a space as written;
- any of those **percent-encoded** (`%2F%2Fevil`, `/%2Fevil`, `/%5Cevil`) and **double or triple encoded** (`/%252Fevil`, `/%25252Fevil`): the path is decoded up to 6 times and every form is checked, with `Uri.decodeComponent` (not `decodeFull`, which leaves `%2F` alone); a malformed escape gives home;
- the sign-in screen itself, also normalised and encoded (`/x/../auth/sign-in`, `/auth%2Fsign-in`, `/%2561uth/sign-in`): it would loop.
The table is in `sign_in_guard_test` (every row is an exact expectation, plus a property test that the answer always starts with one `/` and has no scheme, authority or backslash), and `account_wiring`'s real-route test signs in with four hostile `from`s and ends at home. Protected-ness is judged on the as-written path, its normalised form and its decoded forms, and ignores case, so `/%6De/lists`, `/x/../me/a` and `/ME/a` are guarded too (go_router would not match them anyway; the guard must not depend on that).

## 5. The editor's result after a guard (F-0049 note 11): decision
After a guarded push, `go(from)` replaces the page the call waits for (the call ends with null) and builds the editor with no call, so saving it completes nothing. **Decision: home learns through the `DataChanged('readingLists')` the editor already announces once per save.** `HomePlaceholderPage` listens on the bus; while it awaits an editor it ignores the announcement (the result with the id is on its way), and otherwise shows "Reading lists changed" (key `home.reading_list.changed`). It does not get the new list's id. A real home (the library lists) must reload its lists on that event rather than rely on a call result; the topic string `readingLists` is repeated in the placeholder because a feature's constant is not importable by the app layer (a test in `sign_in_guard_app_test` fails if either drifts). Rejected: threading the `FlowCall` through the guard's `from` (a call is transient and must not survive a redirect: P-095), and a sign-in-first rule that makes the caller sign in before it pushes (it would double the sign-in for every flow).

## 6. Leaving the form mid-request
The form has no back button and "Not now" is ignored while a request runs, and a system back or an iOS swipe is **refused** (`PopScope` for the flow's page, plus a pop entry registered on the flow's outer route, `FlowScope.outerRoute`, which is the route those gestures ask; tested on Android and iOS: the form stays and the sign-in completes). A link or a `go` can still replace the flow. The caller was told "no sign-in", so a sign-in that lands afterwards is **undone, but only the session this request created**: the bloc records `signedInBefore` and the epoch right after its own answer and calls `AuthApi.signOut(ifEpoch:)`, which does nothing when a newer session has started. If someone was signed in before the form opened, the request's sign-in already replaced them, so it **stays: the outcome is B, never signed out**. Details: `AuthSignInBloc._submit` signs out when it finds itself closed (`bloc_guards_test`, and `account_wiring` "leaving the form by Back while the request is on its way"). Without it the answer `false` could be given while a session exists, which the old sheet avoided by answering the real outcome. For this to run the bloc must be closed **with** the flow: **`@disposeMethod Future<void> close()` is required** on a flow's bloc, because injectable registers no dispose for one (the editor has it; the first version of this bloc did not, and the "closed" path never ran).

## 7. Gotchas
- **`gen_l10n` reads a locale out of the file name.** For `auth_sign_in_en.arb` it tries each suffix after an underscore and finds `in_en`, which parses as language `in` (Indonesian), region `EN`: "locale specified in @@locale and the arb filename do not match". Any package whose name contains a segment that is an ISO 639-1 code followed by what parses as a script or region (`_in_`, `_de_`, `_it_`, ...) breaks the same way, and `tool/l10n_check` requires `<package>_<locale>.arb`. The package is therefore `auth_signin`. `mcgen` must reject (or respell) such a name.
- **A form's spinner never settles.** In a widget test a sign-in shows `McFormScaffold`'s spinner until the answer, and the answer needs the session's real file save, so `pumpAndSettle` times out. Steps pump 500 ms (the request on fake time), then `mcFinishStorageIo` (the save on real time), then settle; with a held request (`the backend holds`) two frames are enough. The page shows the spinner for the request only (`isSubmitting: form.isSubmitting`), not for "signed in, page about to leave", so a success settles.
- **Steps with a hyphen:** the BDD generator drops the hyphen from a step phrase ("sign-in" is `signin` in the file name and the function name).
- **Wiring tests have no sign-in route** (a wiring never imports another). `app_core/testing.dart` has `standInSignInRoute()`, a `FlowResultRoute<bool>` like the real one, with a Sign in and a Not now button; wiring tests assert which `reason` it was opened with.
- **Home grew.** The session row (Signed out / Signed in as u-100, Sign in / Sign out) pushed "Open placeholder 7" off the 800x600 test surface: `app_test` scrolls to it now.
- **A guarded cold link to an unknown protected path** (`/library/shelf` is not a route yet) still gets the guard first, then not-found after the sign-in: the guard runs before matching.

## Not done
- No sign-up, password reset or social login (out of scope).
- `go(from)` after a guarded push drops the deep stack the user had (`[home, ...]` becomes `[home, from]`), as a cold link does, and the caller already got null. `pushReplacement` would keep it but breaks the cold link (nothing to replace), so it is not used.
