# F-0071: Characters search: a paged search needs one paging controller per search, and a list keyed by its search

- **Date:** 2026-11-28
- **Author:** crew: Engineer (T-0071)
- **Type:** Lesson / library behaviour
- **Related:** T-0071, T-0046, F-0046, F-0050 section 7, plan 01 section 3.3, `mc_paging`, `mc_fixtures_characters` CONTRACT.md

## Summary
`characters_search` copies the SR exemplar (`discovery_search`) and adds what the exemplar left out: **paging**, and **facets that the backend applies** (a sort order and a team) instead of a client-side filter. Three things were not obvious from the exemplar and cost a round each.

## Facts
1. **One `PagingController` per search, disposed when the search ends.** `PagingController.loadFirst` already drops an older response (its own generation), but it has no "stop, show nothing" call. A clear (back to the recent searches) must also drop an answer that is still on its way. So the bloc creates a controller for each search or facet change and calls `dispose()` on the previous one: its answer is dropped and it stops emitting. The controller reports through `add(_PageChanged(generation, page))`, because only a handler emits; the bloc's own generation (bumped by every search, facet change and clear) drops a page event that was already queued. This is the exemplar's generation guard, one level up.
2. **A new search must start a new list, or it inherits the old scroll position.** With the same `McPagedList` widget kept across `results -> searching -> results`, a fast answer (the in-process backend answers within one frame) means no frame ever draws the spinner, so the list is never unmounted. Its scroll position, past the 80 % load-more threshold of the old list, then asks for page 2 of the new query at once. The first test of "a sort change starts the paging over" caught it (`orderBy=-name&offset=30` was requested). Fix: key the list by `(query, facets)` (`KeyedSubtree(key: ValueKey((query, facets)))`; `CharacterFacets` has value equality). Any paged list that can be replaced by another search needs this.
3. **Reading rows scrolls, and scrolling pages.** A step that checks "the first 30 rows" walks the list with jumps, which crosses the load-more threshold and requests page 2 (and a 152-match query goes on to page 6 if it walks to the end). So scenarios assert the **request counts first** and read rows after, and the row-reading helper (`shownResults`) ends with `mcSettle`, so a page it asked for lands before the test ends (a zero-delay timer was pending otherwise: "A Timer is still pending even after the widget tree was disposed").
4. **Failure kinds `server_error`, `timeout` and `offline` are retried by the client**, so a count of requests after Retry is 4 or more, not 2. Counts that must be exact (a double Retry sends one request) use `malformed`, which is not retried (as the exemplar does).
5. **A facet change restarts the same query; it does not save it again.** The bloc remembers a query once, when its first page has results (`_saved`), reset by a new typed or submitted query and by a clear. A sort or team change on a saved query adds nothing; a query whose first request failed and whose facet change then succeeded is saved by that success.
6. **The team facet is a new fixture filter, and `team` is a team *id*.** `GET /v1/characters?team=` (a team id = the name in lower case with runs of other characters as `-`, so `Harbor Watch` is `harbor-watch`; case-insensitive; empty is no filter; an unknown id is `total: 0`, not an error) was added to `mc_fixtures_characters` with CONTRACT.md and three tests. The synthetic sets give everyone the empty team, so any team filter there matches nothing. The feature keeps its own list of the eight team names (`characterTeams`) and sends `characterTeamId(name)`; contract tests compare both with the fixture (`teamIdOf`, the cast's teams). **Review round:** the first version matched the *name*, but `characters_list` already sent `team=<initialTeamId>`, so one parameter meant two things and a list opened with a team showed an empty grid; its test only asserted the request. Now both send ids, and a `characters_list` scenario opens with `harbor-watch` and asserts the rows (the first 30 of that team, nothing else). An id no team has (`red`, `blue`, used by an older flow test) matches nothing.
7. **`/characters/search` before `/characters/:id`.** In the typed route tree the static `search` child is declared first; the wiring test opens `/characters/search` and asserts no profile was built. Link back stacks follow from the nesting: a cold `miniclient://app/characters/search?q=a` opens `[home, characters list, search]`.
8. **`AnalyticsFlowObserver` needs `RootImport<AnalyticsTracker>` and the route's name must equal the flow page's name** (`characters_search`), or the screen is tracked twice (ADR-0012). The app-wide route-name test (`analytics_screens_test`) lists every route name, so a new route edits it.
9. **Chips in scrolling rows.** Eight team chips do not fit one row at 2x text, so each facet group is a horizontally scrolling row (`SingleChildScrollView` over `McChipGroup`), and steps `ensureVisible` a chip before tapping it. `nothing overflows` holds in `de` and `en_XA` at 1x and 2x.
10. **A shared-feature change moves goldens.** Adding the app-bar search action to `characters_list` changed three of its four goldens by 151 px each (the icon). They were regenerated with `bazel run //feature/characters/characters_list:golden_test -- --update-goldens`; before and after images are in the evidence folder.
