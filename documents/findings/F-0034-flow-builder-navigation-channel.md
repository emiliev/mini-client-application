# F-0034: flow_builder 0.1.0 takes over `flutter/navigation` and drops deep links (T-0035)

Found by the T-0033 Verifier (R1), root-caused and fixed in T-0035, 2026-11-25. Flutter 3.47.7.

1. **Root cause.** `FlowBuilder.initState` calls `SystemChannels.navigation.setMethodCallHandler` with its own handler and never restores the framework's. That handler knows `popRoute` and `pushRoute`; the engine sends deep links as `pushRouteInformation`, so they were answered with `null` and dropped, for the rest of the process, even after the flow is gone. Cold-start links still work (they arrive before any flow).
2. **Accepted deviation (TL): no restore, `state` dropped.** The framework's handler cannot be captured. It is `WidgetsBinding._handleNavigationInvocation` (private) and neither `MethodChannel` nor the messenger has a getter for a registered handler (only `TestDefaultBinaryMessenger.checkMockMessageHandler`, which compares). "Save and restore the original on dispose" is therefore not possible without rewrapping `PlatformDispatcher.onPlatformMessage`. The fix instead makes flow_builder's handler forward every method to the same `WidgetsBinding` entry points as the framework's, so the channel behaves as without a flow whether or not a flow is mounted. Known gap: `pushRouteInformation.state` is dropped (`handlePushRoute` takes a location only; iOS sends none).
3. **Fix: vendor, not wrap.** `third_party/flow_builder` is a pub workspace member named `flow_builder` (`resolution: workspace`), so `pubspec.lock` only loses its hosted entry and `MODULE.bazel.lock` only loses the `pub_deps__flow_builder` repo. `mc_feature_flow` depends on `//third_party/flow_builder`. A fix inside `mc_feature_flow` (re-installing a handler after mount) hits the same missing-capture problem and would have to reimplement `pushRouteInformation` anyway.
4. **Vendored code and the lint aspects.** `build --config=lint` runs `dart_format` and `dart_analyze` over every `flutter_library`. Upstream is neither formatted for Dart 3.13 nor clean under `mc_analysis`, so the target carries `tags = ["no-dart-analyze", "no-dart-format"]` (rules_dart's tags); it still compiles. This keeps `lib/` equal to the archive plus a 17-line patch. `tool/checks/T-0035-AC4_provenance.sh` enforces it.
5. **Test route.** The framework's real path is `tester.binding.defaultBinaryMessenger.handlePlatformMessage('flutter/navigation', JSONMethodCodec().encodeMethodCall(...), ...)`, reaching a `MaterialApp.router` (any `RouterDelegate` that records `setNewRoutePath`). On stock 0.1.0 four of the six `flow_navigation_channel_test` cases fail: a link while mounted, a link after dispose, the nested case and the unknown-method reply (`null`, not `false`). The legacy `pushRoute` case and the `popRoute` interception pass on stock, which is why they are controls.
6. **Upstream.** Draft `documents/upstream/U-X-flow_builder-navigation-channel/` proposes a `WidgetsBindingObserver` instead of a channel handler, at the price of pop ordering (the flow's interceptors would run after the root router's observers, which is worse on Android).
7. **Upstream quirks we did not change** (TL, T-0035; a pending-work item tracks them): popping the flow's own last page at its root is not handled by the flow, so the first `popRoute` there falls through to the router; a hidden inner flow (for example in an `IndexedStack`) still takes the first `popRoute`, because its interceptor stays registered; stock answered an intercepted `popRoute` with `null`. The last one is the exception we did change: it now answers `true`, since iOS treats any other reply as unhandled (`framework_navigation_baseline_test` and `T-0035-AC2` cases).
8. **Tests do not depend on order.** The static handler stays installed once any flow has mounted, so a "behaves as without a flow" comparison inside the flow test file would compare the patched handler with itself. The framework's replies are therefore recorded in `framework_navigation_baseline_test` (its own Bazel target, where no `FlowBuilder` ever mounts) and the flow tests compare with those constants. Mutants of the patch (reply `null`, fragment dropped, intercepted pop answering `null`) are each killed: `documents/evidence/T-0035/engineer/mutants/`.
9. **Stale `PopScope` after a state-driven return (T-0036, patch change 4).** `_canPop` is read while `FlowBuilder` builds, when the navigator still has the old routes, so after `controller.update` returns the flow to its root `PopScope(canPop: false)` stays mounted and eats the next pop (the first tap of the flow's back button, and the iOS edge swipe). Fix in the vendored copy: a post-frame `setState` recomputes `_canPop`, and `_ConditionalPopScope` always mounts the `PopScope` and toggles `canPop`. The always-mounted scope also stops the navigator from being re-parented (and every page rebuilt) when the condition flips; that rebuild had been hiding F-0035's bug. Tests: `flow_kit_test` T-0036-AC1; mutation "no canPop recompute" is killed. Upstream draft updated.
