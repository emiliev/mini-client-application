# F-0036: `McFlowBackButton` follows the outer route, is safe outside a flow, and has a defined precedence (T-0037)

Found by the T-0036 Verifier (R-1 to R-7) and the TL `/code-review` at `cbadeb0`, fixed in T-0037, 2026-11-26. Flutter 3.47.7.

1. **The root button read the outer navigator without a dependency.** `outer.canPop()` was called in `build` with nothing to rebuild the button when the routes below the flow changed. A router `go`, a deep-link stack rebuild (`[flow]` to `[home, flow]` under the same page key) or `removeRoute`/`pushAndRemoveUntil` below a pushed flow left the button stale in both directions: missing when it should be there, visible (and leaving to nowhere) when it should be gone. Today's exemplar is not affected (it is pushed and never rebuilt below), the bricks would be.
2. **Fix.** `FeatureFlow` now calls `ModalRoute.of(context)` for its own route (inside the `FutureBuilder`, so the dependency exists whatever the snapshot) and publishes `outerCanPop: route != null && !route.isFirst` in `FlowScope`. `FlowScope.updateShouldNotify` is also true when that value changes, and the button reads the scope with `FlowScope.maybeOf` (a dependency). `ModalRoute`'s own inherited status notifies when `canPop` flips, which Flutter does when the routes below change, so no `NavigatorObserver` is needed. `route.isFirst` is read instead of `outer.canPop()`: the navigator's `canPop` also counts local history on the first route, which is not "a route below the flow". `di()` still uses the non-listening `FlowScope.read`, so a scope change does not rebuild `BlocProvider.create` callers.
3. **Safe outside a flow (R-5).** On a first route with no `FeatureFlow` above it the button does a nullable lookup (`FlowScope.maybeOf`) and falls back to the AppBar's own logic: `DrawerButton` with a drawer, else nothing (a non-first page gets `BackButton` / `CloseButton`). It never throws. The doc comment says it is safe on every page.
4. **Precedence on the flow root (R-4).** The order is: (1) a local history entry (`route.willHandlePopInternally`, e.g. `showBottomSheet`): a plain `BackButton`, which removes the entry and stays in the flow; (2) a drawer: `DrawerButton`, as `AppBar` does (this changes R-4: a pushed flow root with a drawer used to get the flow's back button); (3) the flow's outer back button, when `outerCanPop`; (4) nothing. Local history wins even over a drawer (the user is "in" the sheet). The outer button calls `maybePop`, so the outer route's `PopScope` is asked (R-1: a `pop` mutation is killed by a test with `PopScope(canPop: false)` around the flow).
5. **flow_builder `didUpdateWidget` had the stale read as well (patch change 5).** `FlowBuilder(state: n, ...)` driven from a parent replaces `_pages` in `didUpdateWidget`; the build that follows reads `_canPop` while the navigator still has the old routes, so two pages to one left `PopScope(canPop: false)` mounted and the next pop (`popRoute`, the iOS edge swipe) was swallowed. The same post-frame `setState` as in `_listener` is now scheduled from both branches of `didUpdateWidget` (new `state`, new `controller`) through one helper, `_recomputeCanPopAfterFrame`. The patch is renamed to `0001-navigation-channel-and-popscope.patch` (it carries more than `pushRouteInformation`, R-6), and the provenance check now also fails when the directory holds anything but that one patch. `VENDORED.md` and the upstream draft are updated.
6. **The always-mounted `PopScope` is pinned (R-3).** A test asserts that `FlowBuilder` has exactly one `PopScope` below it with one page (`canPop: true`), two pages (`canPop: false`) and one page again, and the stock "swap the widget" form is a killed mutation. (The first version of that test assumed `canPop: false` with one page; it is `true`, because `_canPop` looks at the flow's own navigator.)
7. **What the tests had to discriminate.** The `[home, flow]` test needs the same flow page key and the same flow widget instance, so the route is kept and only `isFirst` changes. A `Navigator` with `pages:` (not an imperative push) is what a router does. The `removeRoute` variant has the flow become the first route without the page API. In an `AppBar(leading:)` slot the box is forced to 56 px by the slot, so "empty" is asserted as a `SizedBox` with no child, and in the "outside any route" test the widget sits under an `Align` (not a `SizedBox`), so the assertion is on the widget's own output (R-7 and the TL's AC4 point).
8. **The T-0036 mutation script was superseded.** Its mutations named widget text that no longer exists (`outer.canPop()`, the old `if (route.isFirst) {`). `documents/evidence/T-0037/engineer/mutations.sh` carries T-0036's still-meaningful mutations (isFirst ignored, fullscreen dialog, the flow_builder recompute) re-expressed, plus one or more per TL decision, and `T-0036-AC3_gates.sh` runs it instead of the T-0036 one (the T-0036 file is left on disk as history).
9. **`T-0036-AC3_gates.sh`: a missing file failed silently.** The stale-comment greps were `grep -q ... "$file" && hits+=...`; a moved or renamed file made `grep` exit 2, which looked like "no stale phrase". A missing file is now a recorded failure (negative: `AC4_gates_missing_file_negative.md`).
10. **An open drawer is a local history entry (review round).** `DrawerController` adds a `LocalHistoryEntry(impliesAppBarDismissal: false)`, so `route.willHandlePopInternally` is true while a drawer opens, is open and closes. Branch 1 therefore turned the leading into a back arrow. The check is now `willHandlePopInternally && impliesAppBarDismissal`, as `AppBar` does, so a real `showBottomSheet` entry still gives the plain back and a drawer's own entry is ignored (also for an `endDrawer`-only Scaffold).
11. **`isFirst` is pinned.** An app-root flow whose own outer route holds a local history entry has `Navigator.canPop()` true and `route.canPop` true, but nothing below the flow. A test pins that no button shows; swapping `!route.isFirst` for either of those is a killed mutation.
12. **Nested navigators.** `FlowScope` carries a `NavigatorObserver` that `FeatureFlow` attaches to the flow's own navigator; the flow-root branch is taken only when `route.navigator` is that navigator (`FlowScope.isFlowNavigator`). The first route of a plain `Navigator` nested in a flow page follows the AppBar's default logic. A scope built without the observer (a test double) says yes.
13. **Rebuild scope.** `ModalRoute.of` was called in the `FutureBuilder` builder, so every `isCurrent` change (a dialog opening above the flow) rebuilt the flow navigator. It now lives in a small `_FlowScopeHost` that receives the already-built `FlowBuilder` as `child`; only the scope is republished. The test counts rebuilt elements through `debugOnRebuildDirtyWidget` and expects no `FlowBuilder`. Outside a flow, `impliesAppBarDismissal` is pinned too (a history entry that does not imply dismissal gives no back button).
