# F-0038: Session, bearer refresh and identity fixtures: design facts and gotchas

- **Date:** 2026-11-26
- **Author:** crew: Engineer (T-0039)
- **Type:** Lesson
- **Related:** T-0039, plan 01 U08 / U17 / D-09 / P1-05 AC2 / R29, F-0017, F-0019, F-0024, F-0030

## Summary
`mc_session`, `mc_api_auth` and `mc_fixtures_identity` are pure Dart, registered in the root list, and tested with real concurrent Dio requests on the mocked backend. Five facts are worth keeping: (1) boot-time file I/O hangs `testWidgets`, (2) the refresh is one shared future plus a token comparison, (3) refresh tokens in the mock rotate, and the mock had to survive its own restarts, (4) the root order differs from plan 01, (5) `McTestContainer` does not know the session yet.

## Evidence and facts
1. **Real file I/O during boot hangs a `testWidgets` body.** `Session.restore` reads the saved session through `FileStore` (real `dart:io`). Under fake async the read completes in real time, which no `pump` waits for, so `BootBloc` hit its 10 s timeout and 3 existing targets failed (`app_core:boot_test`, `mini_client:app_test`, `links_after_flow_test`; the rest of `boot_test` failed with "resetDIContainer() was called while initializeDIContainer is running"). `SessionDIInitializer` therefore skips the read when the storage directory is missing or has no entries (`existsSync` / `listSync`, both synchronous): nothing can be saved there. Every widget test with a fresh temp directory and every first launch takes that path. **A test that boots with a populated storage directory under `testWidgets` must drive boot inside `tester.runAsync`.** A real fix is a synchronous `FileStore.readSync` (P-follow-up, not done: `mc_storage` was outside T-0039's edit list).
2. **Concurrent 401s: one `Future<_Refresh>?` field, plus a token comparison.** The first 401 for a request that carried our bearer starts the refresh and stores its future; every other 401 awaits that same future. A 401 that arrives after the refresh finished no longer finds the future, but its request was sent with the old token, which differs from the session's current one, so it is replayed without a refresh. Tested with 3 simultaneous requests (traffic `[401, 401, 401, 200, 200, 200]`, one refresh call), with seeded latency, and with a gated request answered after the refresh (`/v1/gated`). The replay carries a flag, so a replay that gets a 401 again is not refreshed again.
3. **What counts as "the refresh failed".** The server rejecting it (a 4xx, a malformed answer, or no refresh token) clears the session, publishes `SessionChanged(signedOut)` and fails the original request with the original 401 (`ApiFailure.unauthorized`). **Offline, timeout and 5xx on the refresh keep the session** and fail the request with that failure (`ApiOffline`, ...), because signing a user out of a flaky connection is worse than a failed request. The task text says only "refresh fails"; this is the one place the code is more careful than the AC (TL approved 2026-11-26; AC2 on main now says so).
4. **Interceptor order is `[monitoring, retry, auth]`.** The auth interceptor goes last (`ApiAuthDIInitializer` adds it to the registered `Dio`). A replay uses `dio.fetch`, so it passes through every interceptor again and `onRequest` puts the current token on it. A header the caller set itself is left alone and never refreshed. A 5xx retry by `RetryInterceptor` keeps the bearer.
5. **Mock refresh tokens rotate (one use).** Tokens are `mc-access-<user>-<n>` / `mc-refresh-<user>-<n>` with `n` from a per-backend counter, `mc-access-<user>-expired` is the expired form, and validity is by shape, not by remembered state. Shape-only validity is required because the backend starts empty on each app launch while the session file persists. Rotation made a collision visible: after a restart the counter restarts at 1, so refreshing the persisted `mc-refresh-u-100-1` minted `mc-refresh-u-100-1` again, which was already revoked, so the next refresh failed. The counter now skips numbers whose refresh token is revoked (test: "a refresh token saved by an earlier run still works once").
6. **Root order differs from plan 01 §3.4.** `Session` needs `FileStore` and `EventBus`, so the list is Config, Monitoring, Storage, **EventBus**, Session, MockedBackend, ApiClient, ApiAuth. The plan has EventBus after the API client. Plan 01 should follow.
7. **`McTestContainer.initializers` (mc_test_utils) does not register the session or the interceptor yet** (F-0024 item 2: it repeats the root list by hand). Feature tests that need a signed-in user, such as the SC exemplar's favourite, need `SessionDIInitializer` and `ApiAuthDIInitializer` added there, and the drift-guard test F-0024 proposed would have caught it.
8. **Tokens are stored as plain JSON** in the app's support directory (`mc_storage`). Fine for a mock identity; a real provider needs the Keychain (noted in the `Session` doc comment).
9. **`dart_test` for a package that uses `mc_api_client` needs Bazel**, not `dart test`: `api_page.g.dart` is generated by a Bazel action (T-0032), so `dart test` in `mc_api_auth` fails to load. `mc_session` and `mc_fixtures_identity` run with plain `dart test` too (fast loop).

## Implications / actions
- Add `FileStore.readSync` (or a synchronous restore) and drop the "empty directory" shortcut; until then, see fact 1.
- Add `SessionDIInitializer` and `ApiAuthDIInitializer` to `McTestContainer` before the SC exemplar.
- Add `IdentityMockDomain` to the app's `appMockDomains` when the first sign-in UI lands (this task only registers the initializers, so the app's backend does not serve identity routes yet).
- Update plan 01 §3.4 for fact 6.

## Fix round (Verifier FAIL on AC2, `/code-review`)
10. **A refresh outcome belongs to the session it started for.** `SessionReader.epoch` changes on every sign-in and sign-out (not on a refresh). A request records the epoch when the bearer is applied; the refresh starts for that epoch (one shared in-flight future per epoch); `updateTokens(tokens, epoch:)` and `signOut(ifEpoch:)` do nothing for a stale epoch. So a late success cannot overwrite user B's tokens and a late rejection cannot sign B out (Verifier V-P4a, b, c, e are committed in `auth_races_test.dart`).
11. **No cross-account replay.** A 401 is refreshed or replayed only while its epoch is current; otherwise it reaches the caller untouched. The same rule is applied in `onRequest`: a retry (by `RetryInterceptor`) of a request sent for another session is failed as `unauthorized` instead of being sent with the new user's token; a retry after a plain sign-out goes out without the old token.
12. **Single-use bodies.** A `FormData` is cloned for the replay (as in F-0017 #6); a `Stream` body is never refreshed or replayed.
13. **Rejected vs unavailable.** Sign out for `ApiUnauthorized`, `ApiMalformed` and a 4xx other than 408 and 429. Everything else (offline, timeout, 5xx, 429, an unexpected error such as a dropped socket or a cancel) keeps the session and passes the failure through.
14. **A `Future` created at boot is dead for a real-time caller under fake async.** `Session` used to build its save queue (`Future<void>.value()`) in the constructor, which runs inside `testWidgets`' fake zone; a later `tester.runAsync` call chained on it and never completed. The queue is now created on first use, in the caller's zone. This bites any object built during boot that keeps a `Future` field.
15. **`SessionDIInitializer` checks the session's own file** (`FileStore.existsSync('session')`, new, in try/catch), not the directory listing, so unrelated saved keys no longer move boot onto the real-I/O path.
16. **A repeat `signIn` of the same user** replaces the tokens and starts a new epoch but does not announce `SessionChanged(signedIn)` again; a different user does.
17. **`McTestContainer`** now has EventBus, Session and ApiAuth in root order (8 initializers); feature tests sign in with `diContainer<AuthApi>()` inside `tester.runAsync`.
